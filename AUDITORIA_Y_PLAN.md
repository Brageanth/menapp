## Qué es la app

Planificación de menú semanal + despensa + lista de compras + metas nutricionales (yo/pareja) + captura de facturas con OCR + biblioteca de recetas + avisos por Web Push + ajuste de recetas con IA.

## Decisiones de arquitectura (cerradas)

- **Auth:** 1 solo login por hogar (Supabase Auth, magic link). "Yo"/"Pareja" son 2 filas de datos de metas nutricionales, no 2 cuentas ni roles.
- **Metas nutricionales:** 100% manuales. El usuario ya trae sus macros (nutricionista externo), la app solo las setea. Sin IA, sin upload de foto/PDF para extraerlas.
- **Offline-first:** fundacional, no pulido final. Capa IndexedDB (Dexie) como fuente de verdad local para lecturas; cola de escrituras pendientes que sincroniza contra Supabase cuando hay red. Se construye en F0, todas las fases siguientes lo heredan.
- **Mobile-first:** PWA instalable (manifest + service worker/Workbox), no app nativa. Diseño ya es 390×844.
- **Costo:** mantener en free tier siempre que se pueda.
  - Vercel Hobby (free).
  - Supabase free tier (Postgres + Auth + Storage 1GB).
  - Push notifications: Web Push API nativo del navegador (gratis, sin servicio de terceros).
  - Modelos IA: Claude Haiku (vía `@ai-sdk/anthropic` directo, `ANTHROPIC_API_KEY`) para las 3 features IA — son llamadas puntuales de bajo volumen (2 personas), no justifican un modelo grande.
  - Sin add-ons de pago (sin Resend pago, sin push pago, sin DB managed de pago).

## Riesgos / rabbit holes a vigilar

- OCR de factura: precisión variable. Fallback manual siempre visible, nunca debe bloquear el flujo.
- Generación de menú con IA en modo "solo lo que tengo": validar que la IA no invente ingredientes fuera de despensa/biblioteca antes de aplicar el resultado.
- Captura de foto de factura offline: se guarda en cola, pero el OCR requiere red — la UI debe mostrar "pendiente de conexión" explícito, nunca fallar en silencio.
- Sync entre los 2 dispositivos del hogar: **resuelto en F11** — last-write-wins por `updatedAt` al pullear (`src/data/sync-pull.ts`), ver nota técnica en F11.

## Stack

- Next.js (App Router) + Vercel, Node runtime.
- Supabase: Auth + Postgres + Storage (fotos de factura).
- Dexie (IndexedDB) para la capa local-first + cola de sync.
- AI SDK + `@ai-sdk/anthropic` directo, modelo Claude Haiku, para OCR, generación de menú y ajuste de receta.
- Web Push API nativo para notificaciones.

**Bug crítico encontrado y arreglado (2026-10-07): el sync a Supabase nunca había funcionado.** Dos causas combinadas desde F0:
1. Cada repo (`inventory-repo.ts`, `recipe-repo.ts`, etc.) mandaba el objeto de dominio camelCase (`expiresAt`, `prepTimeMinutes`, `personLabel`...) directo como payload del upsert, contra columnas Postgres snake_case (`expires_at`, `prep_time_minutes`, `person_label`...) — PostgREST rechaza esas escrituras, así que las 7 tablas de Supabase estuvieron siempre en 0 filas pese a que la app se usó normalmente (todo vivía solo en IndexedDB).
2. `registerSyncListeners()`/`registerPhotoQueueListener()` solo se llamaban desde `useEffect` de `/hoy` — si la PWA abría en otra pestaña primero, la cola de sync nunca arrancaba esa sesión.

Fix: cada repo ahora tiene `toRow`/`fromRow` explícitos (mapeo camelCase↔snake_case) para push y pull; `enqueueWrite` dispara un `flushQueue()` inmediato en vez de esperar al evento `online`; un componente `SyncManager` (montado en `(tabs)/layout.tsx`, no en una pantalla específica) registra los listeners una sola vez para toda la sesión y corre una reparación de una sola vez (`src/data/resync.ts`, flag en `localStorage`) que limpia la cola rota y re-sube todo lo que hubiera local. Se agregaron columnas faltantes en Supabase (`recipes.protein_tag`, `receipts.error`) que el dominio ya esperaba pero el schema no tenía. **Cualquier repo/tabla nuevo debe definir su propio `toRow`/`fromRow` — nunca pasar el objeto de dominio tal cual a `supabase.from(...).upsert()`.**

**Fixes mobile 2026-10-07 (varias pantallas, no solo F1):** reportes de zoom al tapear rápido y bottom nav que "se bajaba" en vez de quedar fija. Causas: inputs con `fontSize` inline <16px disparaban el auto-zoom de iOS Safari al enfocar (`inventory-form-sheet.tsx` y otros, ahora forzado a `16px !important` en `globals.css`); faltaba `touch-action: manipulation`/`-webkit-tap-highlight-color: transparent` global; y el contenedor raíz de `(tabs)/layout.tsx` usaba `minHeight: 100dvh` con un hijo `flex:1` sin `min-height: 0` — el bug clásico de flexbox, el hijo no se encogía cuando el contenido era más alto que el viewport y empujaba todo (incluido el nav) hacia abajo, scrolleando la página entera en vez de solo el contenido. Cambiado a `height: 100dvh` + `minHeight: 0` en el hijo scrolleable. En `/semana` además se agregó `touch-action: pan-x` al contenedor de los 7 días (scroll horizontal anidado dentro del scroll vertical del layout, gesto ambiguo sin esa declaración). Sin verificar aún en hardware real.

### F8 — Notificaciones (4–5 días) ✅
Avisos_B: alertas por reglas sobre inventario+lista (comprar hoy, vence pronto, bajo stock), configuración de márgenes y hora diaria, delivery vía Web Push.
Entregable: avisa antes de que algo se dañe o falte. **Hecho** — `domain/notification.ts` calcula las 3 reglas (vence pronto por `expiringMarginDays`, bajo stock por `lowStockThreshold`, ítems de compra sin marcar) de forma pura, reusada tanto en la vista previa de `/avisos` como en el cron server-side, para no duplicar la lógica. `notificationSettingsRepo` (Dexie v3 + Supabase, fila única `id: 'default'`) guarda la config igual que los demás repos (`toRow`/`fromRow`). `src/lib/push-client.ts` pide permiso y suscribe el dispositivo a Push API del navegador; `public/sw.js` ganó los listeners `push`/`notificationclick`. `/api/push/subscribe` y `/api/push/unsubscribe` guardan/borran la suscripción en `push_subscriptions` (Supabase, vía sesión de cookies del usuario). `/api/notifications/run` es el cron (protegido con header `Authorization: Bearer CRON_SECRET`): usa un cliente Supabase con `SUPABASE_SERVICE_ROLE_KEY` (sin sesión de usuario, por eso no puede usar el cliente anon normal) para leer despensa/lista/config/suscripciones, calcula las notificaciones del día, las manda con `web-push`, y loguea en `notifications` (tabla ya existía desde F0) con `type: "daily-digest:YYYY-MM-DD"` para no mandar dos veces el mismo día.
Notas técnicas que importan para fases siguientes: **Vercel Hobby limita los cron jobs a 1 ejecución por día** — `vercel.json` define `"0 13 * * *"` (13:00 UTC, fijo), así que el campo `dailyHour` que el usuario configura en `/avisos` es solo informativo/aproximado, no dispara el envío a esa hora exacta; si se necesita hora exacta por usuario hay que pasar a un plan de pago o a un servicio externo de scheduling. Se agregaron 2 tablas a Supabase (`push_subscriptions`, `notification_settings`), mismo patrón de política RLS `"household access"` (`auth.uid() is not null`) que las 7 tablas existentes desde F0 — cualquier tabla nueva debe copiar esa misma política, no inventar otra. Las rutas API que tocan Supabase sin sesión de usuario (el cron) nunca deben importar `@/data/local-db` ni los repos de `src/data/repositories/` — esos importan Dexie, que no existe en el runtime de Node/Vercel Functions; en su lugar se mapean las filas a mano dentro de la route, mismo patrón que ya usaba `/api/generate-menu`.

### F10 — Compartir completo (3–4 días) ✅

Entry point principal: botón "Compartir" en el header de Semana (con acceso a menú + lista de compras de la semana ya cargados). Entry point secundario: botón "Compartir" en Receta_B, que abre el mismo componente pero con `allowedTabs={['receta']}` (solo esa receta, sin cargar menú/semana/lista — no tiene esos datos en ese contexto). `/compras` se migró a reusar `buildShoppingListShareText`/`shareViaWhatsApp` en vez de tener su propia función de texto duplicada; `CATEGORY_LABELS` se movió de ahí a `domain/shopping-list.ts` (export) para que `share.ts` lo reuse sin duplicar las 4 categorías.
Notas técnicas que importan para fases siguientes: `CompartirSheet` recibe los datos ya cargados por props (mismo patrón que `GenerarMenuSheet`/`MenuSlotSheet`, nunca fetch propio) — si una fase futura agrega un nuevo entry point, cargar los datos en esa pantalla y pasarlos, no hacer que el sheet llame a los repos. `allowedTabs` (default las 4) es la forma de restringir qué tabs tiene sentido mostrar según qué datos trae el caller; si faltan `dates`/`menuDays` reales, no incluir esas tabs en `allowedTabs` en vez de pasarles arrays vacíos y dejar que el usuario llegue a un estado vacío confuso.

### F11 — Cool-down: sync fino + costos IA + accesibilidad ✅
Resolución de conflictos de sync entre los 2 dispositivos del hogar, telemetría de costo de las 3 features IA (OCR + generación + ajuste), accesibilidad, performance. Sin features nuevas.

**Sync fino — Hecho.** Se encontró que `pullFromRemote()` existía en cada repo desde F0 pero nunca se llamaba desde ningún lado: la app era push-only, así que el segundo dispositivo del hogar nunca se enteraba de un cambio hecho en el primero. Fix: `src/data/sync-pull.ts` (`mergePulledRows`) aplica last-write-wins por `updatedAt` al pullear — un id con una escritura todavía en la cola local (`pendingWrites`) se saltea siempre (esa escritura no llegó a Supabase todavía, así que el row pulleado está desactualizado por definición y pisarlo tiraría el cambio del usuario), y un id que desapareció del remoto (y no tiene nada pendiente) se borra local — así se propaga un delete hecho en el otro dispositivo. Tablas sin `updatedAt` real (`profiles`, `receipts`, `recipe_versions` — de hecho append-only o de un solo escritor) solo aplican el chequeo de pendientes, sin comparar fecha. `src/data/pull-all.ts` orquesta el pull de las 8 tablas y registra los triggers: foreground (`visibilitychange` a `visible`) y reconexión (`online`) — explícitamente sin polling por intervalo, decisión tomada con el usuario porque es un hogar de 2 personas, no una app realtime. `SyncManager` llama `pullAllFromRemote()` una vez al montar, después del resync de F1.
Notas técnicas que importan para fases siguientes: cualquier tabla nueva con sync debe sumar su `pullFromRemote()` a `pull-all.ts`, y si tiene un `updatedAt` real pasarlo a `mergePulledRows` como tercer argumento — si no se pasa, el merge no compara fechas y el remoto siempre pisa el local (correcto solo para tablas sin ediciones concurrentes reales).

**Telemetría de costo IA — Hecho.** Tabla nueva en Supabase `ai_usage_log` (migración `ai_usage_log`, append-only, sin Dexie/offline-queue — no hace falta offline-first para un log de telemetría, y no importa perder una fila por un corte de red) con el mismo patrón RLS `"household access"` que las demás. `src/domain/ai-usage.ts` tiene el precio de Claude Haiku 4.5 ($1/$5 por millón de tokens input/output, único modelo que usan las 3 features) y `calcCostUsd`. `src/data/log-ai-usage.ts: logAiUsage()` inserta una fila después de cada `generateText` en las 3 routes (`ocr-receipt`, `generate-menu`, `adjust-recipe`) usando `result.usage.inputTokens`/`outputTokens` (AI SDK 7) — nunca rompe la respuesta real si el insert falla, solo loguea el error. `/api/ai-usage-summary` lee la tabla vía `createServerSupabaseClient` (sesión del usuario, no service role — a diferencia del cron de F8, esta ruta sí corre con cookies de sesión) y `/avisos/costos` (link desde Avisos) muestra el total y el desglose por feature, con filtro mes/todo.
Notas técnicas que importan para fases siguientes: si se agrega una 4ª feature de IA, sumar su `AiFeature` al union type y al `check` de la columna `feature` en la tabla (requiere otra migración, no un `ALTER` trivial de agregar valor a enum porque es un `text` con `check`, no un enum real — así se evita la fricción de alterar un enum de Postgres cada vez que se suma una feature).

**Accesibilidad — Hecho (pase acotado, no auditoría completa).** Las 6 sheets de la app (`MenuSlotSheet`, `GenerarMenuSheet`, `AjustarRecetaSheet`, `RecipeFormSheet`, `InventoryFormSheet`, `CompartirSheet`) ganaron `role="dialog"`/`aria-modal="true"` y cierre con Escape — este último centralizado en `useLockBodyScroll(onClose)` (antes no tomaba argumentos) para que las 6 lo hereden gratis en vez de parchear cada una. Botones ícono-only que no tenían `aria-label` (escalar porciones +/− en Receta_B) lo ganaron. El checkbox custom de Compras ahora es `role="checkbox"`/`aria-checked`. El banner de estado de `SyncManager` (sincronizando / cambios pendientes) ahora es `role="status"`/`aria-live="polite"`. `<html lang="es">` ya estaba desde F0. **No se hizo** una auditoría de contraste de color ni un pase con lector de pantalla real — si se reporta un problema de accesibilidad puntual, tratarlo ahí, no asumir que este pase lo cubrió todo.

**Performance — Hecho (pase acotado).** Las sheets pesadas de Semana, Receta_B, Recetas y Despensa (`RecipeFormSheet`, `AjustarRecetaSheet`, `CompartirSheet`, `MenuSlotSheet`, `GenerarMenuSheet`, `InventoryFormSheet`) se cargan con `next/dynamic` en vez de import estático — no hace falta tenerlas en el bundle inicial de una pantalla si el usuario nunca abre esa sheet. Los tipos (`RecipeFormValues`, `InventoryFormValues`) siguen importándose estáticos (`import type`, costo cero en runtime). No se corrió un profiling real ni un análisis de bundle size con herramienta dedicada — si una pantalla se siente lenta en hardware real, medir ahí antes de optimizar más.
Notas técnicas que importan para fases siguientes: toda sheet nueva que se agregue a una pantalla con otras sheets ya dinámicas debe seguir el mismo patrón (`dynamic(() => import(...).then((m) => m.X))`), no volver a import estático.
